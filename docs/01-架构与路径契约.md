# 01 — 架构与路径契约

## 1. 这个发行版由什么组成

```
用户侧
  DSH Desktop (Electron 44；Portable 实机记录为 DSH 0.2.0-rc.2，
               RC3 的静态/隔离协议验证在 DSH 0.2.1-rc.2 上完成)
    └─ profile: <DSH_HOME>\profiles\<profile>\
         ├─ package.json          dependencies + dsh.profile.bundles
         ├─ pnpm-lock.yaml
         └─ node_modules\@local\dsh-cnki-research  ==> junction ==> <安装根目录>\bundle\cnki-research
                        │
                        └─ Cordis loader 读 cordis.patch.yml
                             └─ preset-cnki-research  (@deepseek-ai/dsh-agent-preset)
                                  └─ 仅在 CNKI Research 会话的 scope 里激活
                                       ├─ cnki-mcp  (@deepseek-ai/dsh-mcp-client, stdio)
                                       │     └─ 子进程: <安装根目录>\.venv\Scripts\python.exe
                                       │                 <安装根目录>\bundle\cnki-research\launcher\cnki_research_launcher.py
                                       │                   └─ 复用 cnki-mcp 的 McpToolService
                                       │                        └─ Playwright Chromium（按需启动，可见窗口）
                                       └─ skill-filesystem (customSkillDirs = <bundle>\skills)
```

要点：

* **一个** MCP 子进程服务所有 CNKI Research 会话，浏览器操作在它内部串行；
* 子进程在 Preset 卸载时才被销毁；
* `cnki_mcp` 包安装在 `<安装根目录>\.venv` 的 `site-packages` 里（`--no-editable`），
  因此 venv 可以整体搬动；
* 上游源码 `<安装根目录>\upstream\cnki-mcp\` 只作为 GPL 源码提供与重建依据，
  运行期不需要它存在（但卸载时若不 `-PurgeRuntime` 会保留）。

> 以上是**运行期**结构。统一安装/升级包在它之外增加了一层**包级布局**：
> `PackageRoot`（新解压的发行树 + 包内发布元数据）可以与 `InstallRoot`（正在使用的安装根）
> 分离，安全升级就发生在“从 PackageRoot 读取目标字节、写入 InstallRoot”的过程中。
> 包级布局、哈希闭包与升级引擎契约见 §8、§9。

## 2. 为什么路径必须全部在运行期解析

`cordis.patch.yml` 是**被安装到别人电脑上**的文件。如果里面写了
`<盘符>:\<开发目录>\...` 这样的绝对路径，那么在别的电脑上：

* 安装目录不同 → MCP 子进程根本起不来（`command` 不存在）；
* 启动器路径不同 → `args[0]` 指向不存在的文件；
* Skill 目录不同 → `customSkillDirs` 静默失效，技能不出现。

更糟的是这些错误在 YAML 层面看不出来：DSH 只会在 MCP 连接失败时降级为"暂无工具"，
使用者看到的是"插件装了但没有工具"。

所以本发行版把每一个位置都改成运行期求值。求值机制来自 DSH 自身：
`@deepseek-ai/cordis-plugin-loader` 的 `interpolate()`
（`src/config/utils.ts:12-22`）会递归遍历整个 entry config，把任何
`{__jsExpr: "..."}` 节点替换为 `evaluate(ctx, expr)` 的结果，`ctx` 里带有
`baseUrl`（当前 profile 目录的 file URL）。

```js
// cordis-plugin-loader/src/config/utils.ts
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) { return eval(expr) }
`)
export function interpolate(ctx, object, value) { /* 递归替换 __jsExpr */ }
```

`!!js` 这个 YAML 标签由 `@deepseek-ai/dsh-app-boot` 注册
（`lib/index.js:20-26`，`kind: "scalar"`），所以块标量（`!!js |-`）也被接受，
这也是本发行版把长表达式写成可读块标量的原因。

## 3. 路径契约表

| 配置位置 | 取值方式 | 失败时的降级 |
|---|---|---|
| `skill-filesystem.config.customSkillDirs[0]` | `dirname(require.resolve('@local/dsh-cnki-research/package.json'))/skills`；回退 `<baseUrl>node_modules/@local/dsh-cnki-research/` | 返回字面量 `skills` |
| `cnki-mcp.config.args[0]` | 同上 + `/launcher/cnki_research_launcher.py` | 返回文件名 |
| `cnki-mcp.config.cwd` | 同上（bundle 目录本身） | 返回 `.` |
| `cnki-mcp.config.command` | 见下 | 返回 `python` / `python3` |

### `command` 的解析顺序

1. 环境变量 `CNKI_RESEARCH_PYTHON`
2. `<bundle>/portable.runtime.json` 的 `python` 字段（安装器写入）
3. `<安装根目录>/.venv/Scripts/python.exe`（`<bundle>/../../`）
4. `<安装根目录>/.venv/bin/python`
5. `<bundle>/../.venv/Scripts/python.exe` 与 `.../bin/python`（另一种目录布局）
6. PATH 上的 `python`（Windows）/ `python3`（其他）

每个候选都要通过 `fs.existsSync` 才会被选中；前 5 步全部落空时回退到 PATH，
**不会抛异常**。这一点至关重要：表达式抛异常会让整个 entry config 求值失败，
Preset 激活随之失败。静态测试 A7 的 `totalFallback` 子项专门验证"什么都解析不到时
仍然返回可用字符串"。

## 4. 为什么用 `link:` 而不是复制

`dsh plugin --profile X add "link:<绝对路径>"` 让 pnpm 在 Profile 的
`node_modules\@local\dsh-cnki-research` 建一个 **junction** 指向
`<安装根目录>\bundle\cnki-research`。

好处：

* 安装根目录里的 `portable.runtime.json`、`_portable\install-state.json` 与
  Profile 里看到的是同一份内容，不会出现"两份配置不一致"；
* 更新发行包时只要替换安装根目录，Profile 立刻看到新内容；
* 卸载时删链接即可，不涉及复制体的生命周期问题。

代价：安装根目录不能随意删除。移动后需要重新执行 `-Action install`
（或直接 `dsh plugin ... add` 指到新位置）。

原安装器 `tools\portable.ps1`（LEGACY）也支持 `-LinkMode copy`（`file:` 前缀），此时 Profile 拥有独立副本，
搬动安装根目录不会影响已安装的插件，但两份配置会各自独立。

## 5. 隔离模型（为什么不会污染 Standard / Creator）

1. 所有插件行都是 `preset-cnki-research` 这个 `@deepseek-ai/dsh-agent-preset`
   声明的**子行**。激活发生在 Preset 自己的 Cordis scope 里
   （`dsh-agent-preset-registry` 的 `createScope(owner, key)`），**从不进入根组合**。
2. 工具可见性沿 scope 链合并，因此 `mcp__cnki__*` 只出现在 `agentPreset` 为
   `cnki-research` 的会话。
3. MCP `serverName` 预约按 scope 隔离（`activeServerNames` WeakMap），
   与根作用域的同名实例不会冲突。
4. 安装只写 Profile 的 `package.json` / `pnpm-lock.yaml` / `node_modules`，
   **不修改** Profile 的 `cordis.patch.yml`，不动内置 Preset。

## 6. 从 v1.1 故障中吸取的经验（只读参考，未引入任何 v1.1 代码）

| v1.1 的问题 | 本发行版的处理 |
|---|---|
| 模型工具 Schema 触发 `INVALID_REQUEST` | 实测确认 DSH 对 MCP `inputSchema` **不做任何转换**（`parameters: inputSchema` 是引用别名，唯一改动是一次 `structuredClone`），供应商端点是 Anthropic Messages API，工具项为 `{name, description, input_schema}`。因此新增 `--sanitize-schema` 可选路径，把 `anyOf: [X, {"type":"null"}]` 折叠为 `X` 并去掉 `title`；默认关闭以保留 v1.0 行为。两种形态都由 `tests/test_tool_schema.mjs` 验证。 |
| 模块解析失败 | 本发行版不引入任何 Host 端 JS 模块解析；插件是纯配置型 bundle（`dsh.bundle.patch`），只挂载 DSH 自带插件。 |
| 冷启动验收 | 增加了与 DSH 解耦的 stdio MCP 探针（`tools/probe_mcp_stdio.py`）与 `--selfcheck`，可在安装前独立运行。 |
| 使用 Host Runtime Plugin 扩展 Preset | **不采用**。全部能力通过既有 `@deepseek-ai/*` 插件行实现。 |

## 8. 统一包布局（PackageRoot / InstallRoot）与哈希闭包

### 8.1 两个根

| 名称 | 含义 | 默认值 |
|---|---|---|
| `PackageRoot` | 解压出来的统一发行包根：既是**安装源**，也是**升级目标字节的来源** | `tools\` 的上级目录（`setup.ps1` 自动推导） |
| `InstallRoot` | 正在使用的安装根（Layout A） | 全新安装默认 = `PackageRoot`（“解压即安装”）；升级时必须显式给出旧 RC2 安装根 |

* 全新安装允许 `PackageRoot == InstallRoot`（原地安装）。
* **升级要求两者是彼此独立的目录**：相等、互为祖先/后代、或包根/安装根出现重解析点
  （junction/symlink）组合一律拒绝（fail-closed），从机制上阻止“把新 ZIP 解压覆盖旧安装”。
* `setup.ps1 -Action check` 在 `PackageRoot == InstallRoot` 且发现安装标记时
  **拒绝**（exit 2）并给出指引，不尝试修复混合目录。

### 8.2 包内容（metadata-split）

统一发行 ZIP 解压后 = **RC3 发行树** + **包内发布元数据**：

| 类别 | 内容 | 是否安装到 InstallRoot |
|---|---|---|
| 发行载荷 P（115 个文件） | 冻结 RC3 的 107 个载荷 + 8 个统一新增载荷（`tools/setup.ps1`、`tools/lib/UpgradeCommon.ps1`、`tools/build_unified_release.ps1`、`tests/Test-UnifiedMatrix.ps1`、`tests/lib/UnifiedFixtures.ps1`、`tests/lib/UnifiedAssert.ps1`、`tests/Test-UnifiedVerification.ps1`、`tests/test_unified_package.mjs`） | 是 |
| `manifest.json` | 分发清单：`schemaVersion 1`；`files[]` 恰好描述 P（逐文件 `path`/`bytes`/`sha256`）；`install.entryPoint = tools/portable.ps1`；新增 `install.setupEntryPoint = tools/setup.ps1` 与 `upgrade` 元数据块 | 是（安装根保留一份） |
| 发布元数据 | `SHA256SUMS.txt`、`upgrade-data/rc2-to-rc3.json`、`upgrade-data/README.md` | **否**（永不复制） |

* ZIP 内**没有** `payload/` 之类的目标文件副本；升级目标字节直接读取
  `<PackageRoot>\<相对路径>`。
* 安装/升级完成后 InstallRoot 的发行文件集合 = P + `manifest.json`
  （外加安装器维护的 `.venv\`、`_portable\`、`bundle\cnki-research\portable.runtime.json`）。
* 若升级前 RC2 安装根里存在 P 之外的**用户文件**：引擎不会删除它们；无法归类的额外文件
  会按检测规则报告（可能使状态变为 `UNKNOWN_OR_MODIFIED`，fail-closed）。

### 8.3 哈希闭包（无环）

```
外部 ZIP SHA-256（<zip>.sha256 + 发布级 SHA256SUMS.txt）
        │ 锚定
        ▼
包内 SHA256SUMS.txt ──覆盖──► { P, manifest.json, upgrade-data/rc2-to-rc3.json, upgrade-data/README.md }（除自身）
        │
        ▼
manifest.json ──files[]──► P（115 个载荷的逐文件哈希）
        ▲
        │ targetManifestHash = sha256(manifest.json)（可内嵌，因为 manifest 不哈希 upgrade-data）
upgrade-data/rc2-to-rc3.json ──expectedTargetHashes（115 项）──► 与 manifest.files[] 逐项相等
```

* `upgrade-data/rc2-to-rc3.json` **不包含**自身哈希、`manifest.json` 哈希、`SHA256SUMS.txt`
  哈希或目标 ZIP 哈希（避免循环）；`changedFiles` 里 `manifest.json` 的目标哈希就是
  `targetManifestHash`，其余载荷使用内嵌的目标哈希。
* 目标 `manifest.json` 的身份由“`SHA256SUMS.txt` 中的 manifest 条目 + 目标哈希与
  `manifest.files[]` 的一致性”共同证明；发布级身份最终由外部 ZIP SHA-256 锚定。

## 9. 升级引擎与事务契约（由 Upgrader V1 适配的派生作品）

### 9.1 来源与许可

`tools/lib/UpgradeCommon.ps1` 是本项目 **Upgrader V1**（同一 GPL-3.0-only 项目）的**派生作品**：
保留其事务状态机、planId 门、备份/暂存校验、原子替换、回滚与用户数据保护等全部安全语义，
只做两类适配：**包布局解耦**（目标字节来自 PackageRoot 而非补丁包 `payload/`）与
**新增文件（`operation: "add"`）语义**。V1 独立补丁包的测试结论**不自动**迁移到本统一包，
统一包必须按 A–K 矩阵重新执行。

### 9.2 动作、状态与写入范围

* 动作：`check` / `plan` / `apply`（由 `setup.ps1 -Action upgrade` 路由）/ `verify` / `status` / `rollback`。
  `check` / `plan` / `status` / `verify` **只读**（不建文件、不写日志）。
* 状态机：`NOT_INSTALLED`（安装推荐）/ `RC2_CLEAN` / `RC2_HOTFIXED`（2 个 `cordis.patch.yml`
  字节级变体）/ `RC3_ALREADY_INSTALLED`（变体 `UNIFIED` 或 `FROZEN_RC3`，安全 no-op）/
  `UNKNOWN_OR_MODIFIED`（fail-closed，输出冲突清单）。
* 写入白名单：变化载荷（15 个 RC3 相对 RC2 已变化 + `m` 个统一版再次编辑 + 8 个新增）+
  `manifest.json` + 2 个环境元数据（`_portable\install-state.json`、
  `bundle\cnki-research\portable.runtime.json`）。
* 只读/禁写：`.venv\`、`_portable\backups\`、`_portable\upgrades\` 以外的 `_portable` 内容、
  DSH home、`.cnki-mcp`、Playwright 目录、Profile junction 目标路径。

### 9.3 事务与回滚

* 事务目录：`<InstallRoot>\_portable\upgrades\<transactionId>\`（`transaction.json` + `backup\` +
  `staging\`），创建时绝不覆盖既有事务；阶段：
  `PRECHECKED → BACKED_UP → STAGED → APPLYING → APPLIED → VERIFIED → COMMITTED`；
  失败 → `FAILED_RESTORED` / `FAILED_MANUAL`；回滚 → `ROLLBACK_STARTED → ROLLED_BACK` /
  `ROLLBACK_FAILED_MANUAL`。
* 备份/暂存都逐文件复核哈希；替换是原子的；**版本标记（`VERSION`、`manifest.json`）最后写**；
  提交前跑全量目标状态 VERIFY，确保不出现“版本标记已是 rc.3、内容仍是 RC2”的混合安装。
* 新增文件回滚：仅当当前字节 == 已应用目标哈希时删除；被用户改过 → 冲突拒绝 + 人工指引；
  只清理本事务创建的空目录（精确路径，不递归删除用户内容）。
* planId 门：PLAN 生成 `planId`，APPLY 必须提供且与当前状态重算值一致；状态变化 → `PLAN_STALE`。
* DSH 运行门：真实生产 home + DSH 进程运行 → 拒绝 APPLY/ROLLBACK（`DSH_IN_USE`）；
  隔离目标 + DSH 运行 → WARN 放行；绝不强杀进程、不写 Profile 触发 HMR。
* 安全实现约束：Windows PowerShell 5.1；离线；CHECK/PLAN/APPLY/VERIFY/STATUS/ROLLBACK
  不联网、不派生需要的外部工具进程；不使用 `Remove-Item -Recurse`；不做重解析点递归遍历。

### 9.4 与安装器/统一入口的关系

* `setup.ps1` 只做**状态识别 + 路由 + 门禁 + 统一 JSON/退出码**；升级逻辑在引擎内，不重复实现。
* 全新安装/卸载/安装器回滚仍由 `tools/portable.ps1` 执行（字节不变，语义不变）。
* 完整命令与流程见 `docs/04-升级与版本维护.md`，测试口径见 `docs/05-测试报告.md`。
