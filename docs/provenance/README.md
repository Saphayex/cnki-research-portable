# docs/provenance — 来源与完整性记录 / Provenance and integrity records

本目录是**只读的来源记录**，用于回答两个问题：

1. 本发行版所基于的冻结 v1.0 生产插件，究竟是哪几个字节？
2. 随包内置的上游 `cnki-mcp` 源码，究竟来自哪一份内容？

## 本目录包含

| 文件 | 内容 |
|---|---|
| `v1.0-bundle.sha256.json` | 冻结基线 `@local/dsh-cnki-research@1.0.0` 的 5 个文件的字节数与 SHA-256 |
| `upstream-src.sha256.json` | 内置上游 `cnki-mcp` 源码树的 63 个文件的字节数与 SHA-256 |

这两份文件只包含**路径、字节数与哈希**，不包含任何机器名、账号、机构或登录状态。
`manifest.json` 的 `baseline` 字段即由 `v1.0-bundle.sha256.json` 生成，`tests/test_static_package.mjs`
的 A1 / A5 组会在每次运行时重新核对这些哈希。

> **`upstream-src.sha256.json` 的范围。** 它记录的是**封装上游时**实际核对过的 63 个文件
> （`src/` 与 `tests/`）。此后为修复上游 README 中指向 `docs/api.md` 的链接、并让上游文档保持
> 完整，同一版本的 `docs/api.md` 也被纳入 `upstream/cnki-mcp/`；该文件由 `manifest.json`
> 逐文件哈希覆盖，但**不在**上面这份 63 条的历史记录中。上游其余文件（`LICENSE`、
> `pyproject.toml`、`uv.lock`、`README.md`、`.gitignore`）同样由 `manifest.json` 覆盖。


## 本目录**不**包含的内容

原始基线审计记录（`audit-v1.0.md`）是一份面向维护者的工作底稿：它逐条引用了**构建机**
上的绝对路径、构建机所属机构以及 DSH 安装位置，用于说明「为什么这样设计」。

该文件**不随本仓库发布**，原因是它是开发机专属记录，而不是用户文档；公开发布它只会
暴露维护者的机器布局，对使用者没有任何价值。需要该记录的维护者应从私有归档中获取。

因此：

* 公开仓库与本目录**不**提供该审计底稿；
* **`v1.0.0-rc.2` 的发行 ZIP 由本仓库原样构建**，因此同样**不含**该底稿——RC2 起压缩包内容与
  公开仓库逐字节一致，不存在"包内有、仓库内无"的文件；
* 历史上的 `v1.0.0-rc.1` 压缩包曾包含该文件（它由清理前的构建树打出，已被 RC2 取代），
  该版本仅作内部历史产物保留，不再对外发布；
* 本目录的**哈希记录完整保留**，基线可被任何人独立复核，不依赖那份底稿。

## 如何复核

```powershell
# 逐文件核对整个载荷（含本目录的两份哈希记录）
node tests\test_static_package.mjs
```

任何不一致都会以 `FAIL` 报出并以非零退出码结束。
