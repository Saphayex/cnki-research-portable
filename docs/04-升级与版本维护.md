# 04 — 升级与版本维护

面向两类人：**使用者**（全新安装 / 从 RC2 安全升级 / 退回）与**维护者**（构建、发布与版本约定）。

本版最重要的变化：包内新增**统一入口** `tools\setup.ps1`。
同一份统一发行 ZIP 同时支持**全新安装**与**已有标准 RC2 安装的安全原地升级**；
原有 `tools\portable.ps1` 的命令与语义**逐字节保留**，其中 `-Action upgrade` 是
**LEGACY（重装覆盖）**，不是安全增量升级。

> 文档中的 `setup.ps1` 均指 `<PackageRoot>\tools\setup.ps1`（`PackageRoot` = 你解压出来的
> 统一发行包目录）；`<RC2 根>` 指现有 `1.0.0-rc.2` 原地安装根（Layout A）。

---

## 1. 使用者视角

### 1.1 先选对入口

| 你的情况 | 该怎么走 | 是否会写文件 |
|---|---|---|
| 没装过，全新安装 | `setup.ps1 -Action check` → `plan` → `install -Yes` | check/plan 只读；install 会写 |
| 已有 `1.0.0-rc.2` **标准原地安装（Layout A）** | `check -InstallRoot <RC2 根>` → `plan -InstallRoot <RC2 根>` → 退出 DSH → `upgrade -PlanId -Yes` | 前三步只读（upgrade 前必须退出 DSH） |
| 已经是 RC3（统一版） | `setup.ps1 -Action check`；无需操作 | 只读；upgrade 是安全 no-op |
| 已经是 RC3（旧冻结版） | 同上：核心版本已完整，无需操作 | 只读；已知限制：不会自动补装统一工具链新增文件 |
| 检测为 `UNKNOWN_OR_MODIFIED`（被修改/混合/损坏） | 停止；按 §1.5 处理 | 拒绝写入 |
| Layout B（`-InstallRoot` 独立运行根） | 增量升级不支持；按 §1.4 人工迁移 | — |

退出码（统一入口与引擎一致）：`0` 成功 / 无需操作；`2` 被拒绝 / 有 FAIL / 冲突 / 状态未知；
`1` 工具内部错误。加 `-Json` 或 `-OutFile <路径>` 可得机器可读报告。

### 1.2 全新安装

```powershell
# 解压到空目录后：
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action check
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action plan
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action install -Yes -AllowProductionProfile
# 独立 Profile 试装：... -Action install -Yes -DshProfile cnki-trial
# 离线（uv 缓存已预热）：... -Action install -Yes -Offline
```

* `check`/`plan` 只读；`install` 委托原安装器完成 venv、Chromium 与 `dsh plugin` 注册。
* 安装到真实 `desktop` Profile 时 `-AllowProductionProfile` 必须由**用户本人**授权。
* 完整步骤见 `README.md` 第 3.1 节与 `DEPLOYMENT_README.md`。

### 1.3 从 RC2 安全原地升级（核心流程）

**适用范围**：现有安装满足 **Layout A**——安装根里同时有：
`VERSION`、`manifest.json`、`bundle\cnki-research\{package.json,cordis.patch.yml,launcher\…,skills\…}`、
`upstream\cnki-mcp\`、`docs\`、`tests\`、`tools\`，以及安装器运行期产物
`_portable\install-state.json`、`bundle\cnki-research\portable.runtime.json`、`.venv\`、
`_portable\backups\`。安装根路径在升级前后**不变**。

**整包流程**：

```powershell
# 0) 把统一发行 ZIP 解压到一个全新的空目录（作为 PackageRoot；不要覆盖旧安装目录）

# 1) 只读 CHECK：识别来源状态并做包完整性/路径/环境检查
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action check -InstallRoot "<RC2 根>"
#    期望 sourceState = RC2_CLEAN 或 RC2_HOTFIXED：
#      RC2_CLEAN   = 107 个 RC2 载荷逐字节匹配
#      RC2_HOTFIXED= 仅 cordis.patch.yml 为 2 个白名单热修字节变体之一，其余 106 个仍匹配 RC2
#    若为 UNKNOWN_OR_MODIFIED：停止，按 §1.5 处理。

# 2) 只读 PLAN：生成 planId，列出将替换/新增的文件、备份位置与环境元数据更新
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action plan -InstallRoot "<RC2 根>"
#    期望 exit 0；输出 planId（下一步必须原样使用）。

# 3) 正常退出 DSH（等它完全关闭；不要强杀进程，不要改 Profile 触发 HMR）

# 4) 独立 PowerShell 窗口执行 APPLY（事务化；必须带 -PlanId 与 -Yes）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action upgrade -InstallRoot "<RC2 根>" -PlanId "<planId>" -Yes
#    期望 exit 0：输出 transaction id、阶段 COMMITTED、文件级升级完成提示。

# 5) 正常重新打开 DSH → 新建 CNKI Research 会话 → 验收 8 个工具随后：
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action verify -InstallRoot "<RC2 根>"
#    期望 FILE_UPGRADE_COMPLETE = PASS
#    DSH_RUNTIME_ACTIVATION_VERIFIED = NOT TESTED（需要你的人工实机验收，工具不代为声明）

# 6) 如需退回 RC2（逐字节回滚，含删除本次新增的文件）：
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action rollback -InstallRoot "<RC2 根>" -Yes
```

**升级写入什么**（白名单，其余一律不写）：

* 变化的发行载荷：15 个 RC3 相对 RC2 已变化的文件 + 统一版新增/编辑的文件（含 8 个新增文件）；
* `manifest.json`（目标分发清单，最后写）；
* 2 个环境元数据：`_portable\install-state.json`（`distribution` → `1.0.0-rc.3`，追加 `upgrade`
  记录）、`bundle\cnki-research\portable.runtime.json`（`distribution` → `1.0.0-rc.3`，
  追加 `upgradedAt`/`upgradedBy`；文件不存在则跳过并告警，不创建）。

**升级不会碰什么**：

* `.venv\`、Playwright/Chromium、`_portable\backups\`；
* DSH Profile（`package.json`、`pnpm-lock.yaml`、`node_modules` junction）——不写、不重跑
  `dsh plugin`、不触发 HMR；
* DSH 的 sessions/storages/credentials、`%USERPROFILE%\.cnki-mcp` 登录态、用户自己的文件；
* 安装根路径保持不变，因此 `link:<RC2 根>\bundle\cnki-research` 引用与 junction **不需要重建**。

**为什么可以不重装环境**：`bundle/cnki-research/**`（含 `cordis.patch.yml`、launcher、skills）与
`upstream/cnki-mcp/**`（含 `uv.lock`）在本版本中与冻结 RC3 **逐字节一致**，
RC2→RC3 的语义变化只有 cordis persona 的一行删除；因此不需要 `uv sync`、不需要下载 Chromium、
不需要重新登录。

**事务与回滚**：

* 升级前先做**逐文件备份**并复核哈希；目标字节先 staging 校验、再原子替换；
  版本标记最后写；提交前做全量目标状态 VERIFY。
* 事务目录：`<RC2 根>\_portable\upgrades\<transactionId>\`（`transaction.json` + `backup\` +
  `staging\`）。**不要手工删除**——它是回滚与人工恢复的依据。
* 失败时自动恢复（`FAILED_RESTORED`）；无法安全确认时停在 `FAILED_MANUAL` 并打印人工恢复命令，
  不强行清理现场。
* `setup.ps1 -Action rollback -InstallRoot "<RC2 根>" -Yes` 会优先使用最近的升级事务做
  **逐字节**回滚；回滚新增文件时只删除“升级前不存在且当前字节仍等于已应用目标哈希”的文件，
  被用户改过的文件会被保留并报告冲突。

**必须遵守的边界**：

| 场景 | 行为 |
|---|---|
| `PackageRoot` 与 `InstallRoot` 相同、互为祖先/后代，或含重解析点组合 | **拒绝**（不升级） |
| 把新 ZIP 解压覆盖旧安装根 | 混合状态，`check`/`plan`/`upgrade` **拒绝**；不自动修复 |
| 来源状态不是 `RC2_CLEAN` / `RC2_HOTFIXED`（含 Layout B、未知、混合、被修改） | **拒绝**并输出冲突清单 |
| 已有 upgrade 事务未完成/损坏 | **拒绝**新事务；按 `status`/`verify` 输出与人工指引处理，或先 `rollback` |
| 真实生产 home + DSH 正在运行 | APPLY 拒绝（`DSH_IN_USE`）；隔离目标 + DSH 运行 → WARN 放行 |
| `-PlanId` 缺失、过期或与当前状态不符 | 拒绝（`PLAN_ID_REQUIRED` / `PLAN_STALE`），重新 `plan` |
| 磁盘空间不足/无写权限 | 预检拒绝或事务失败并自动恢复；按输出处理，勿手工拼装文件 |

### 1.4 已经是 RC3（统一版 / 冻结版）与 Layout B

* **RC3_ALREADY_INSTALLED（统一版）**：安装内容与统一发行包的 `manifest.json`/载荷精确一致。
  `check` exit 0；`upgrade` 是安全 no-op（`NOOP_ALREADY_TARGET`：不建事务、不备份、不写文件）。
* **RC3_ALREADY_INSTALLED（冻结版）**：安装内容与**旧冻结 RC3** 的 107 载荷 + 冻结
  `manifest.json` 精确一致。同样安全 no-op；已知限制：**不会自动补装统一工具链新增文件**
  ——核心功能版本已完整，无需操作即可继续使用。若确实需要统一工具链，请按“全新安装”到新目录
  或走人工迁移，不要手工往安装根里复制文件。
* **Layout B（`-InstallRoot` 独立运行根）**：增量升级不支持（来源判定为
  `LAYOUT_SEPARATE_PACKAGE_ROOT`）。人工方案：
  * **B-1（刷新运行根内容，推荐给不想挪 Profile 的用户）**：在 DSH 退出后，用统一包对旧运行根
    执行一次安装器重装：
    `powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action install -Force -InstallRoot "<旧运行根>" -Yes`
    （需要用户授权生产门禁时追加 `-AllowProductionProfile`；venv 健康时复用，不保证完全离线）。
    该操作把运行根内容刷新到目标版本，但**不改变它仍是 Layout B 的事实**；今后每次升级都需重复，
    直到迁移为 Layout A。执行前请确认 Profile junction 指向 `<旧运行根>\bundle\cnki-research`。
  * **B-2（迁移为 Layout A，推荐长期方案）**：把统一包解压到新目录并**原地安装**（不传
    `-InstallRoot`，即新目录成为 Layout A 安装根），再通过一次官方插件管理操作让目标 Profile
    指向新根（`dsh plugin add`，属于 Plugin Manager/ Creator 场景）。此后即可使用
    `setup.ps1 -Action upgrade` 的增量升级。该方案会新建 venv，需要网络与重新验收。

### 1.5 状态未知 / 被修改（UNKNOWN_OR_MODIFIED）

检测不是只看 `VERSION` 或某个字符串，而是“布局 + `manifest.json` 哈希 + `VERSION`/distribution +
逐文件哈希 + 新增文件存在性”的联合判定。出现未知状态时：

1. **不要**手工编辑安装根、Profile 或 `manifest.json` 试图“修好”；
2. 阅读 `check` / `plan` 输出的 `conflicts[]`（哪些文件与 RC2/RC3 都对不上）；
3. 可选用恢复路径：
   * 有原始 RC2 ZIP 时：解压到**新的空目录**，按 RC2 文档原地安装，再执行 §1.3 升级；
   * 没有干净的 RC2 时：直接**全新安装**统一版到新目录（会重建 venv，需要网络与重新验收），
     再通过插件管理操作切换 Profile；
4. 升级器与安装器都会**拒绝覆盖**用户修改；这是设计行为，不是故障。

### 1.6 卸载与回滚（两套机制）

| 场景 | 命令 | 恢复什么 |
|---|---|---|
| 卸载插件（全新安装后） | `setup.ps1 -Action uninstall -Yes` | 移除 Profile 注册与自身 junction/运行时文件；默认保留 venv（`-PurgeRuntime` 才删） |
| 撤销升级（升级后回 RC2） | `setup.ps1 -Action rollback -InstallRoot "<RC2 根>" -Yes` | 最近的升级事务，逐字节恢复 RC2 载荷与环境元数据，并删除本次新增文件 |
| 撤销安装（安装器备份） | `setup.ps1 -Action rollback -Yes` | 安装器 `_portable\backups\<时间戳>\` 中的 Profile 文件 |
| 指定回滚方式 | `-RollbackTarget upgrade|install|auto`（默认 `auto`） | `auto`：有升级事务优先事务回滚，否则安装器备份回滚 |

注意：`rollback` 是**写操作**，需要 `-Yes` 或交互确认；`-DryRun` **不会**被转发给
`portable.ps1 -Action rollback/uninstall`（旧安装器这两个动作的 DryRun 可能仍写备份）。

### 1.7 查看版本 / 状态 / 诊断

```powershell
# 统一状态：安装版本、来源状态、DSH 引用、升级事务历史
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action status -Json
# 只读兼容性/环境检查
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action check
# 升级后的文件级验证
powershell -NoProfile -ExecutionPolicy Bypass -File tools\setup.ps1 -Action verify -InstallRoot "<RC2 根>"
# 旧安装器的状态/诊断仍然可用（字节未变）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action status
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action diagnose
```

### 1.8 只升级 cnki-mcp（不换发行包）

发行包固定 `cnki-mcp 0.1.1`。如果上游发布了修复版而发行包还没更新，可以：

```powershell
# 1) 选一个可写位置作为新的安装根目录
# 2) 用原安装器 tools\portable.ps1（LEGACY）的 -Upstream pypi -UpstreamVersion <版本> 重装
powershell ... -File tools\portable.ps1 -Action install -Upstream pypi -UpstreamVersion 0.2.0 -Force
```

或者直接在现有 venv 里升级后用原安装器 `tools\portable.ps1 -Action diagnose` 复核：

```powershell
<InstallRoot>\.venv\Scripts\python.exe -m pip install -U "cnki-mcp==<版本>"
powershell ... -File tools\portable.ps1 -Action diagnose
```

> 注意：用原安装器 `tools\portable.ps1` 的 `-Upstream pypi` 时 `uv.lock` 的精确固定不再生效，
> `install-state.json` 里的 `packages` 字段会记录实际装上的版本；
> **这样会改变 venv，安全升级的环境不变式不再成立**，生产使用建议等发行包更新。

## 2. 维护者视角

### 2.1 目录职责

| 路径 | 谁改 |
|---|---|
| `bundle/cnki-research/**` | 插件本体：Preset 声明、启动器、Skill；**核心文件必须与冻结 RC3 逐字节一致** |

| `tools/portable.ps1`、`tools/lib/PortableCommon.ps1` | 原安装器；**必须保持与冻结 RC3 逐字节一致**（字节漂移会改变发行身份并触发回归） |
| `tools/setup.ps1` | 统一入口：状态识别、路由、门禁、统一 JSON/退出码 |
| `tools/lib/UpgradeCommon.ps1` | 升级引擎（Upgrader V1 的派生作品）；改动必须保留事务/回滚/用户数据保护语义 |
| `tools/build_unified_release.ps1` | 统一构建器：升级元数据 + manifest + SHA256SUMS + 确定性 ZIP + 外部身份资产 |
| `tools/build_manifest.mjs`、`tools/verify_release_zip.ps1` | 清单生成与归档校验 |
| `tools/package_release.ps1`、`tools/build_release_manifest.mjs` | fail-closed 守卫，统一构建请用 `build_unified_release.ps1` |
| `upgrade-data/rc2-to-rc3.json` | **生成物**（由统一构建器生成），不要手改 |
| `SHA256SUMS.txt` | **生成物**（由统一构建器生成），不要手改 |
| `manifest.json` | **生成物**（`node tools\build_manifest.mjs`），不要手改 |
| `tests/**` | 自动测试（`test_static_package.mjs`、`run_all.ps1` 及统一矩阵/验证套件） |
| `docs/**` | 说明文档；`docs/provenance/**` 是冻结记录，**不要改** |
| `VERSION` / `CHANGELOG.md` | 发行版本与变更记录 |

### 2.2 统一构建与发布流程

前置：Windows PowerShell 5.1 + Node（仅构建机需要）；只读输入为冻结 RC2 ZIP 与冻结 RC3 ZIP
（后者用作“核心文件逐字节不变”的等价性 oracle）。**不要**修改/覆盖冻结输入。

```powershell
# 1) 先定稿所有非生成载荷：docs / README / CHANGELOG / tools/setup.ps1 / 引擎 / 测试 …
#    并确认核心文件仍与冻结 RC3 逐字节一致（构建器会重新断言）

# 2) 统一构建：生成 upgrade-data/rc2-to-rc3.json、manifest.json、SHA256SUMS.txt、
#    确定性 ZIP（默认输出到 dist/ 并复制到 OutDir），以及外部身份资产
#    （<zip>.sha256、发布级 SHA256SUMS.txt、RELEASE_MANIFEST.json、DEPLOYMENT_README_release.md）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build_unified_release.ps1 `
  -Rc2Zip "<冻结 RC2 ZIP>" `
  -Rc3FrozenZip "<冻结 RC3 ZIP>" `
  -Repo "<本候选仓库>" `
  -OutDir "<发布资产目录>"

# 3) 清单/载荷一致性
node tools\build_manifest.mjs --check
node tests\test_static_package.mjs
node tests\test_unified_package.mjs

# 4) 归档校验（ZIP 结构、哈希闭包、无内部材料、路径卫生）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\verify_release_zip.ps1 -Zip "<候选 ZIP>"

# 5) 统一测试：升级矩阵 + 全新安装/安装器回归/包完整性/MCP/归档
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-UnifiedMatrix.ps1 -Rc2Zip "<冻结 RC2 ZIP>" -UnifiedZip "<候选 ZIP>"
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-UnifiedVerification.ps1 -UnifiedZip "<候选 ZIP>"
```

构建/发布约定：

* **确定性**：ZIP 条目排序、forward slash、固定 1980-01-01 时间戳、固定压缩、无属性位、无 `.git`；
  两次干净构建必须字节一致（构建器提供复现检查）。
* **版本与身份**：统一构建器在构建机**内部**产出的内部构建产物沿用内部候选文件名
  `CNKI-Research-Portable-1.0.0-rc.3-unified-candidate.zip`（仅构建机内部使用、**不对外发布**，不属于用户可见的下载/校验对象）；
  对外发布的附件名一律为官方发行名 `CNKI-Research-Portable-1.0.0-rc.3.zip`（与内部产物同一字节流）。
  `v1.0.0-rc.3` Tag、push 与 GitHub Release 发布**需要另行批准**，本轮不发布、不推送。
  旧冻结 RC3 的哈希只作为**旧候选身份**审计记录，不复用。发布校验策略：
  ZIP + 同名 `.sha256` sidecar + 发布级 `SHA256SUMS.txt`，**不提供第二份同名 SHA 文件**。
* **不外发内部材料**：审计/规格/证据/构建工作目录/内部报告不得进入 ZIP 或发布资产。
* `upgrade-data/README.md` 不得写入真实的 `manifest.json`/`SHA256SUMS.txt`/元数据/ZIP 哈希。

### 2.3 同步上游新版本

```powershell
# 1) 在别处 clone 上游到目标 commit
git clone https://github.com/sepinetam/cnki-mcp <临时目录>
git -C <临时目录> checkout <commit>

# 2) 只替换这三个部分，不要带入 .git / .venv / __pycache__
#    upstream/cnki-mcp/src
#    upstream/cnki-mcp/tests
```

### 2.6 版本号约定

* `VERSION` / `manifest.distribution.version`：发行版号，语义化版本。本轮保持
  `1.0.0-rc.3`；`manifest.distribution.variant = "unified-installer"` 标记统一安装/升级变体，
  `manifest.distribution.candidate = true` 是构建器保留的**内部候选标记**（仅构建机内部使用、不对外）；
  对外发布的附件名一律为官方发行名 `CNKI-Research-Portable-1.0.0-rc.3.zip`，不再以文件名后缀标记候选状态。
* `bundle/cnki-research/package.json` 的 `version`：插件版本。**只有插件本体
  （Preset / 启动器 / Skill）变化时才递增**；核心 Bundle 仍为 `1.0.0`。
* `manifest.json` 保持 `schemaVersion 1`，只做**加法**扩展：`install.setupEntryPoint`、
  `upgrade` 元数据块（`schemaVersion 2` 的引用、数据路径、引擎路径、源/目标版本、
  允许的来源状态）；`install.entryPoint` 保持 `tools/portable.ps1`。
* `upgrade-data/rc2-to-rc3.json` 是 `schemaVersion 2` 的**生成物**：只由统一构建器生成，
  不要手改；任何载荷字节变化都必须重跑统一构建。
* 静态测试 `A2.identity` 会强制 `VERSION`、`manifest.distribution.version` 与
  `manifest.bundle.version` 三者自洽。
* 若改动只是 Preset 声明中的**提示词变量兼容修复**（如 RC3 删除 DSH `0.2.1-rc.2` 已移除的
  `{{cwd}}` suffix），核心 Bundle 版本仍保持 `1.0.0`：对外暴露的工具、Schema 与功能未变。
  这类改动必须写入 `CHANGELOG.md`，并由 `A7.promptVariables` 回归断言守护。

## 3. 故障与恢复（升级）

| 失败/异常 | 系统留下的状态 | 恢复方式 |
|---|---|---|
| 预检失败（路径/磁盘/权限/包完整性） | 未开始事务，无写入 | 按输出修正条件后重新 `check`/`plan` |
| 备份或 staging 校验失败 | 事务未进入 APPLY，自动回滚/清理 | 查看事务记录与输出；重新 `plan` 后重试 |
| APPLY 中途失败 | 自动恢复（`FAILED_RESTORED`）或停在 `FAILED_MANUAL` | 按输出的人工恢复命令逐条执行；或先 `rollback`；**不要删除事务目录** |
| 崩溃/断电留下未完成事务 | `_portable\upgrades\` 中存在非终态事务记录 | `setup.ps1 -Action status`/`verify` 查看；优先 `rollback` 恢复；不要手工拼接文件 |
| VERIFY 未通过 | 事务未提交，按失败路径恢复 | 保留现场与证据，报告给维护者；不要手工改 `manifest.json`/`VERSION` |
| 回滚冲突（用户改过新增文件） | 回滚拒绝删除被修改文件，`FAILED_MANUAL`/冲突指引 | 保留用户修改并手工核对；不要强制删除 |
| DSH 仍在运行 | APPLY/ROLLBACK 被拒绝（`DSH_IN_USE`） | 正常退出 DSH 后重试（隔离目标只 WARN） |
| 生产门禁 `REFUSED:` | 未写入 | 确认目标后用**用户本人**授权追加 `-AllowProductionProfile` |

更完整的安装器失败表见 `docs/02-安装卸载与回滚.md` 第 7 节（旧安装器语义保持不变）。
