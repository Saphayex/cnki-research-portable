# 02 — 安装、卸载与回滚

所有动作都通过同一个入口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action <动作> [选项]
```

| 动作 | 是否改动系统 | 说明 |
|---|---|---|
| `check` | **否**（只读） | 环境、依赖、完整性、同名插件检查；`-Json` 输出机器可读报告 |
| `plan` | **否** | **`install` 的真实 dry-run**：走同一条代码路径并抑制全部副作用，输出"将要做什么"的步骤清单 |
| `install` | 是 | 建 venv、装依赖、写运行时描述、经官方 `dsh plugin` 安装 Preset |
| `upgrade` | 是 | 同 `install`，用于用新发行版覆盖旧版本（先备份） |
| `status` | 否 | 读 `_portable\install-state.json` 并实时核对 |
| `diagnose` | 否 | `check` + `status` + 启动器 `--check`/`--selfcheck` + MCP 探针 + 孤儿进程 |
| `uninstall` | 是 | 从 Profile 移除插件；默认保留 venv，加 `-PurgeRuntime` 一并删除 |
| `rollback` | 是 | 从备份恢复 Profile 的 `package.json`/`pnpm-lock.yaml` 并修复 `node_modules` |

> `check` / `plan` / `status` / `diagnose` 都**不写** DSH 数据目录、不装依赖、不动 Profile。
> 唯一的文件写入是 `%TEMP%` 下一个用完即删的探针脚本（用于读取 CNKI Profile 列表）。
>
> 退出码：`0` 无 FAIL；`2` 有 FAIL（`check` / `plan` / `install` / `upgrade`）；
> `1` 工具自身出错。`status` / `diagnose` 描述既有状态，恒为 `0`。

常用选项：

| 选项 | 说明 |
|---|---|
| `-InstallRoot <目录>` | 运行时安装位置（默认＝发行包所在目录） |
| `-DshProfile <名字>` | 目标 DSH Profile（默认 `desktop`） |
| `-DshHome <目录>` | 覆盖 `%DSH_HOME%`（默认 `%USERPROFILE%\.dsh`） |
| `-DshCli <dsh.cmd>` | 手工指定 DSH CLI（默认自动发现） |
| `-Python <python.exe>` | 手工指定解释器 |
| `-Uv <uv.exe>` | 手工指定 uv |
| `-CnkiProfile <名字>` | 顺便把该 CNKI Profile 设为默认（**见下方门禁**） |
| `-LinkMode link\|copy` | junction（默认）或 Profile 内独立副本 |
| `-Upstream vendor\|pypi\|git` | cnki-mcp 获取策略（默认 `vendor`） |
| `-Force` | 覆盖已存在的同名安装（会先备份） |
| `-DryRun` | 只打印将要执行的步骤，什么都不做 |
| `-Yes` | 不交互，全部视为同意（供提示词/自动化使用） |
| `-AllowProductionProfile` | **显式授权改动真实用户 DSH 数据目录**（见下方门禁） |
| `-NoToolInstall` | 不自动安装缺失的 uv |
| `-PurgeRuntime` | 卸载时一并删除 venv |

## 0. 生产数据门禁（`-AllowProductionProfile`）

安装器内含一道**硬性保护**，用于防止误操作破坏真实用户数据：

> 任何会改动**真实 DSH 数据目录**（默认 `%USERPROFILE%\.dsh`，其中含
> `sessions\`、`storages\`、`.credentials.yaml`）的操作，
> 在没有显式传入 `-AllowProductionProfile` 时**直接拒绝执行**。

被门禁覆盖的动作与对象：

| 动作 | 受保护对象 | 不加开关的后果 |
|---|---|---|
| `install` / `upgrade` | 目标 Profile 的 `package.json`、`pnpm-lock.yaml`、`node_modules` | `REFUSED:` 并退出 1 |
| `uninstall` | 同上 | `REFUSED:` |
| `uninstall -PurgeRuntime` | 同上 + `.venv` | `REFUSED:` |
| `rollback` | 同上 | `REFUSED:` |
| `install -CnkiProfile <名>` | `%USERPROFILE%\.cnki-mcp\profiles\config.json`（机构登录状态，**不在 `$DSH_HOME` 内**） | `REFUSED:` |

判定"是否为真实环境"的依据（`Test-ProductionTarget`）：

1. 目标 home 等于默认的 `%USERPROFILE%\.dsh`；**或**
2. 目标 home 下已存在**非空**的 `sessions\` 或 `storages\`（说明真实用户用过）。

因此**新建的空目录不会被门禁拦住**，测试与试装无需该开关：

```powershell
# 试装到独立 Profile：不需要 -AllowProductionProfile
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 `
  -Action install -Yes -DshProfile cnki-trial

# 装到日常使用的 desktop Profile：需要显式授权
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 `
  -Action install -Yes -AllowProductionProfile
```

`-Action plan` 与 `-DryRun` **不需要**该开关：dry-run 本来就不改动任何东西，
它只在步骤清单里以 `NOTE:` 形式告诉你"真正执行时需要 `-AllowProductionProfile`"。

其它相关保护：

* **卸载只删自己装的东西**：若 Profile 里指向的 bundle 不是本次安装的位置（例如手工
  搭的插件或冻结的生产 bundle），`uninstall` 会拒绝，除非显式 `-Force`。
* **删 `.venv` 前检查链接**：`-PurgeRuntime` 发现 `.venv` 或其一级子目录含
  junction/symlink 时**拒绝删除**（Windows PowerShell 5.1 的
  `Remove-Item -Recurse` 会跟随嵌套链接，可能删到链接目标里）。
* **`-Json` 不等于同意**：`-Json` 只切换输出格式；只有 `-Yes`（或 dry-run）才会
  自动确认那些会改动环境的提问。

## 1. 安装流程

`-Action install` 的顺序（每一步都会打印 `->` 行）：

1. **核对环境**：等价于先跑一遍 `check`。
2. **解析工具链**：Python ≥ 3.11；`uv` 缺失时按 `manifest.json` 记录的版本
   （`0.12.15`）用 `pip install --user uv==<版本>` 安装，失败再退回普通 `pip`。
   `-NoToolInstall` 可关闭。
3. **同名冲突检查**：若目标 Profile 已存在 `@local/dsh-cnki-research`：
   * 指向**同一个** bundle 目录且版本相同 → 报告"已安装"，直接结束（`-Force` 可重装）；
   * 其他任何情况 → **拒绝覆盖**并说明来源、版本与路径，要求先 `-Action uninstall`
     或显式 `-Force`。**不会**静默覆盖未知版本或不兼容插件。
4. **物化安装根目录**：`-InstallRoot` 与发行包目录不同时，把 `bundle\` 与
   `upstream\` 复制过去。
5. **建立 Python 环境**：
   ```
   uv sync --frozen --no-dev --no-editable --directory <InstallRoot>\upstream\cnki-mcp --python <python>
   ```
   环境变量 `UV_PROJECT_ENVIRONMENT=<InstallRoot>\.venv`。
   `--frozen` 保证严格按 `uv.lock`，`--no-editable` 让包真正装进 venv
   （venv 可整体搬动）。已有健康环境时直接复用。
6. **Chromium**：`%LOCALAPPDATA%\ms-playwright` 下没有 `chromium-*` 时，
   询问后执行 `<venv>\Scripts\python.exe -m playwright install chromium`。
7. **写运行时描述**：`<bundle>\portable.runtime.json`
   （`python` / `launcher` / `installRoot` / `upstream` / 版本 / 时间）。
8. **可选 CNKI 默认 Profile**：`-CnkiProfile` 时调用上游
   `config.set_default_profile()`——只写 `%USERPROFILE%\.cnki-mcp\profiles\config.json`
   并创建目录，**不启动浏览器、不碰登录态**。
9. **备份**：把 Profile 的 `package.json`、`pnpm-lock.yaml`、
   `cordis.patch.yml`、`pnpm-workspace.yaml`、`.plugin-manager\run.json`
   复制到 `<InstallRoot>\_portable\backups\<yyyyMMdd-HHmmss>\`，并写 `backup.json`。
10. **官方安装**：
    ```
    <dsh.cmd> plugin --profile <profile> add "link:<bundle 绝对路径>"
    ```
    失败则**自动用备份恢复** Profile 文件并报错退出。
11. **验证并记录**：确认 Profile 能解析到插件，写 `_portable\install-state.json`
    （含解释器、包版本、备份目录、restart-required）。

`restart-required: false`：DSH 的 `dsh-base` 在任何 profile 启动中都挂载了 `dsh-hmr`，
所以插件安装是热生效的（不需要重启）。若某天 DSH 改变这一行为，安装器会把
`dsh plugin` 的提示原样转达；**任何情况下都不会自动重启 DSH**。

## 2. 安装后要做什么

1. 刷新 DSH 页面（不是重启）。
2. 新建会话，Agent 预设选 **CNKI Research**。
3. 让会话调用 `mcp__cnki__login`，在弹出的 Chromium 窗口里完成机构认证。
4. 认证成功后即可检索。

## 3. 卸载流程

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action uninstall
```

顺序：

1. 备份 Profile（`reason: uninstall`）。
2. `dsh plugin --profile <profile> remove @local/dsh-cnki-research`
   —— 由 pnpm 摘掉依赖与链接。
3. **补漏**：pnpm 摘除 `link:` 依赖后**可能把 junction 留在 `node_modules` 里**
   （实测行为，见第 4 节）。安装器若发现残留，会先确认它是 reparse point，
   再用 `[System.IO.Directory]::Delete(path, $false)` **只解除链接**。
   如果残留物是**真实目录**（`-LinkMode copy` 的情形），安装器**不会**删除它，
   只在报告里提示由使用者自行处理。
4. **验证目标仍在**：打印链接目标是否依然存在。
5. 删除 `<bundle>\portable.runtime.json` 与 `_portable\install-state.json`。
6. 默认**保留** venv 与上游源码；`-PurgeRuntime` 才会删除 venv。

卸载**不会**触碰：

* `%USERPROFILE%\.cnki-mcp\`（你的 CNKI Profile 与登录态）；
* 其他插件、其他 Profile、Profile 的 `cordis.patch.yml`；
* `%LOCALAPPDATA%\ms-playwright`。

## 4. Windows Junction 安全（这是本发行版最小心的地方）

### 4.1 为什么危险

`node_modules\@local\dsh-cnki-research` 是一个 **junction**（目录重解析点）。
对它执行 `Remove-Item -Recurse`、`rmdir /s`、`robocopy /MIR`、`fs.rm(recursive)`
等操作，**有可能递归进入目标目录**，把 `<安装根目录>\bundle\cnki-research`
（甚至其父目录）的内容删掉。

### 4.2 本发行版的做法

* 唯一的链接删除入口是 `Remove-LinkSafely`（`tools/lib/PortableCommon.ps1`）：
  1. 先 `Get-Item -Force` 检查 `FileAttributes.ReparsePoint`；
  2. **不是**重解析点就直接抛错拒绝，绝不动手；
  3. 是重解析点才调用 `[System.IO.Directory]::Delete($path, $false)`
     —— 第二个参数 `false` 表示"不递归"，只删除链接本身。
* 正常路径上甚至不会走到它：移除由 pnpm 完成。
* 静态测试 `A6.entryPoint` 会检查安装器里任何 `Remove-Item -Recurse` 都与
  `Remove-LinkSafely` 同时出现（唯一合法的递归删除是 venv，且删除前也做了
  重解析点判断）。

### 4.3 实测证据

* DSH 自身的移除路径（`dsh-plugin-manager`）不调用任何 `rm`/`rimraf` 处理已安装条目，
  只有 `pnpm remove`。
* 随 DSH 分发的 pnpm 11.7.0 在摘除直接依赖时只用 `unlink`/`rename`。
* 在本机用**同一个** pnpm 做过实验：`add link:<目标>` → junction 建立；
  `remove` → `package.json` 中的依赖项消失、**目标文件全部完好**，
  但 **junction 本身仍留在 `node_modules` 里**（这正是第 3 步的补漏理由）。
* 对照实验：对该残留 junction 执行 `Remove-Item -Recurse` 也没有删掉目标
  —— 但**这是不可依赖的实现细节**，本发行版不采用这种方式。

### 4.4 绝不允许的调用

| 危险调用 | 为什么禁止 |
|---|---|
| `Remove-Item -Recurse <junction>` | 行为取决于 PowerShell/文件系统实现，历史上会删进目标 |
| `rmdir /s /q <junction>` | 同上 |
| `robocopy <空目录> <junction> /MIR` | 会把目标清空 |
| `fs.rm(path, {recursive:true})` 指向链接 | Node 会跟随重解析点 |
| 直接编辑 Profile 的 `package.json`/`cordis.patch.yml` | 绕过官方插件管理器，破坏 pnpm 与 DSH 的一致性 |
| 删除 `.plugin-manager\run.json` | 那是"正在运行的包操作"记录，删掉会让后续操作并发写入 |

## 5. 回滚流程

```
# 用最近一次备份
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action rollback
# 指定某次备份
powershell -NoProfile -ExecutionPolicy Bypass -File tools\portable.ps1 -Action rollback -Backup <备份目录>
```

1. 先给**当前**状态再做一次备份（`reason: pre-rollback`），使回滚本身也可回滚；
2. 用目标备份覆盖 Profile 的 `package.json`、`pnpm-lock.yaml` 等；
3. 执行 `dsh plugin --profile <profile> install` 让 pnpm 按恢复后的清单修复
   `node_modules`；
4. 若第 3 步失败，报告里会给出确切的手工修复命令，且 Profile 清单已经恢复。

`-Action uninstall` 之后想恢复，用最新的 `reason: install` 备份回滚即可。

## 6. 状态与诊断

```
powershell ... -Action status      # 已安装吗？解析到哪个目录？venv 健康吗？
powershell ... -Action diagnose    # 上面全部 + 启动器自检 + MCP 握手 + 孤儿进程
powershell ... -Action check -Json # 只读的兼容性报告，便于交给他机
```

`diagnose` 会额外检查：

* 启动器 `--check`：cnki_mcp / mcp / playwright / Chromium 是否可用，CNKI Profile 状态；
* 启动器 `--selfcheck`：上游 stdio 缺陷是否已修复（决定启动器还需不需要）；
* `tools/probe_mcp_stdio.py`：真实 stdio 握手 + `tools/list` + 资源列表 + 进程清理；
* 是否有残留的启动器进程（"浏览器起不来"的常见原因）。

## 7. 失败恢复

| 失败点 | 系统留下的状态 | 恢复方式 |
|---|---|---|
| `uv sync` 失败 | 无 Profile 改动；可能留下半成品 venv | 重跑 `install`；必要时删掉 `<InstallRoot>\.venv` 再跑 |
| Chromium 下载失败 | 环境已就绪，仅缺浏览器 | `<venv>\Scripts\python.exe -m playwright install chromium` |
| `dsh plugin add` 失败 | 安装器已用备份恢复 Profile 文件 | 看输出里的 pnpm 日志路径；修好网络后重跑 |
| 安装成功但页面无 Preset | Profile 与 bundle 均在 | `-Action diagnose`；刷新页面 |
| 卸载后残留链接 | 安装器报告并只解除链接 | 见上文第 3 步；`-Action diagnose` 可复查 |
| 任何时刻中途中断 | `_portable\backups\` 与 `_portable\install-state.json` 留存 | `-Action rollback -Backup <目录>` |
