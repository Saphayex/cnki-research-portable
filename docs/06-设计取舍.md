# 06 — 设计取舍与上游分发策略

把已验证的 DSH Desktop 插件 [`@local/dsh-cnki-research@1.0.0`](../bundle/cnki-research/)
做成**可跨电脑、可重复部署、可安装卸载**的通用发行版。

* **基线**：冻结的 v1.0 生产插件（发行前的实际安装目录与逐文件哈希记录在
  [`docs/provenance/`](../docs/provenance/)），
  逐文件 SHA-256 记录在 [`docs/provenance/v1.0-bundle.sha256.json`](../docs/provenance/v1.0-bundle.sha256.json)。
  该目录**只读**，本发行版从不修改它。
* **上游**：`cnki-mcp 0.1.1`（GPL-3.0），完整源码内置在
  [`upstream/cnki-mcp/`](../upstream/cnki-mcp/)，逐文件哈希记录在
  [`docs/provenance/upstream-src.sha256.json`](../docs/provenance/upstream-src.sha256.json)。
* **不含**：v1.1 Host Runtime Plugin 的任何代码、配置或依赖。v1.1 只会以
  *故障经验*（工具 Schema、模块解析、冷启动）的形式被参考，见
  [`docs/01-架构与路径契约.md`](../docs/01-架构与路径契约.md) 第 6 节。

## 3. 路径无关

`bundle/cnki-research/cordis.patch.yml` 里**没有任何盘符、用户名或开发目录**。
每一项都在条目激活时解析（`!!js`，由 Cordis loader 的 `interpolate` 求值）：

| 配置项 | 解析顺序 |
|---|---|
| Bundle 目录 | `createRequire(baseUrl).resolve('@local/dsh-cnki-research/package.json')` → `<baseUrl>node_modules/@local/dsh-cnki-research/` |
| `customSkillDirs[0]` | `<bundle>/skills` |
| MCP `args[0]` | `<bundle>/launcher/cnki_research_launcher.py` |
| MCP `cwd` | `<bundle>` |
| MCP `command` | `$CNKI_RESEARCH_PYTHON` → `<bundle>/portable.runtime.json` 的 `python` → `<installRoot>/.venv/Scripts/python.exe` → `.../bin/python` → PATH 上的 `python` |

每个表达式都整体 try/catch，**永远返回字符串**：缺少任何可选文件只会降级，不会让
Preset 激活失败。含空格与中文的安装根目录由
[`tests/test_static_package.mjs`](../tests/test_static_package.mjs) 的 A7 组实证。

安装根目录可以整体搬走：venv 用 `uv sync --frozen --no-editable` 建立，包被真正
复制进 `site-packages`；搬动后 `portable.runtime.json` 里记录的旧解释器路径不存在，
表达式会落到相对路径并继续工作。

## 4. 机构无关

* Preset 描述、Skill、启动器说明里**没有**任何机构名（由静态测试 A3 强制）。
* 发行包不含任何 Cookie、`storage_state.json`、账号或认证文件（由 A4 强制）。
* 默认 Profile 由使用者自己的 `%USERPROFILE%\.cnki-mcp\profiles\` 决定；
  安装器提供 `-CnkiProfile <名称>` 显式指定（只写 `config.json`，不触发浏览器）。
* 首次使用由 `login` 工具弹出浏览器，由使用者本人完成机构 SSO / 验证码。

## 5. 上游分发策略：为什么默认选 A

`cnki-mcp` 是 **GPL-3.0**。三种可行策略：

| 策略 | 许可证合规 | 可复现性 | 安装便利性 | 维护成本 |
|---|---|---|---|---|
| **A. 内置固定版本源码**（默认） | 合规：随包提供完整源码与许可证 | **强**：源码逐文件 SHA-256 + `uv.lock` 冻结全部依赖版本 | 好：解压即装，只需 PyPI 取 wheel | 低：升级时替换源码并重算哈希 |
| B. 安装时按固定 Git commit 自动获取 | 合规 | 中：依赖 GitHub 可达性与该 commit 长期存在 | 差：需要 git/网络，国内网络常不可达 | 中：要维护 commit 与镜像 |
| C. 从 PyPI 按版本安装 | 合规（GPL 允许） | 中：版本可固定，但制品哈希需额外校验 | 好 | 低 |

**默认采用 A**，理由：

1. GPL-3.0 的源码可得性要求由随包源码直接满足，无需依赖外网；
2. `uv sync --frozen` 让**全部传递依赖**也精确复现（`mcp 1.30.0`、`playwright 1.63.0` …）；
3. 上游源码在本机没有 Git 元数据（不含 `.git` 目录），按 commit 固定无法从本机获得
   可靠的 commit id；
4. 目标用户常处于 GitHub 不可达的网络环境。

同时**支持** B / C 作为备选：`-Upstream pypi`（按 `manifest.json` 记录的版本，配合
已核验的 wheel SHA-256）与 `-Upstream git -UpstreamCommit <sha>`。见
[`docs/04-升级与版本维护.md`](../docs/04-升级与版本维护.md)。

## 6. 安装路径

一律使用 DSH **官方**插件管理接口，不手工改 Profile 配置：

```
dsh plugin --profile <profile> add "link:<bundle 的绝对路径>"
```

该命令把剩余参数转发给 Profile 目录里的 pnpm，并在成功后把包名加入
`dsh.profile.bundles`。安装器在此之上加了：安装前备份、完整性校验、
失败自动恢复、同名插件冲突拒绝（默认不覆盖）。

## 7. 安全边界（发行版自身的设计约束）

* 卸载只用 pnpm 或 `Directory.Delete(path, recursive: false)` 处理 **junction 本身**；
  没有任何代码路径会对可能是指向真实目录的链接做递归删除。
  实测证据与不安全调用清单见 [`docs/02-安装卸载与回滚.md`](../docs/02-安装卸载与回滚.md) 第 4 节。
* 不删除使用者已有的 CNKI 登录态、其他插件或其他 Profile。
* 所有失败路径都在 `<安装根目录>\_portable\` 下留下 `install-state.json`、
  `backups\<时间戳>\` 与 pnpm 日志路径。
